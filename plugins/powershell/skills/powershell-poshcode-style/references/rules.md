# PowerShell Practice and Style rules (condensed)

Every rule from the PowerShell Practice and Style guide, including separately labeled unpublished TODO proposals. Those proposals are not adopted policy unless the user chooses them.

Examples are omitted. ## Quick rules

- Follow the repository's established layout when it differs from this guide. — Maintain Consistency in Layout ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#maintain-consistency-in-layout)).
- Separate reusable tools from scripts orchestrating one workflow; controllers may write interactive displays or unattended logs. — TOOL-01 Decide whether you're coding a 'tool' or a 'controller' script ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#tool-01-decide-whether-youre-coding-a-tool-or-a-controller-script)).
- Check for a suitable existing command before implementing another; learning, missing functionality, and defects can justify a replacement. — WAST-01 Don't re-invent the wheel ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#wast-01-dont-re-invent-the-wheel)).
- Prefer a suitable native PowerShell operation over external facilities; the guide itself labels this preference debatable. — PURE-01 Use native PowerShell where possible ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#pure-01-use-native-powershell-where-possible)).
- Check built-in command capabilities before constructing a wrapper for an external alternative. — PURE-04 Wrap other tools in an advanced function or cmdlet ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#pure-04-wrap-other-tools-in-an-advanced-function-or-cmdlet)).

## Tooling

- Choose the oldest practical PowerShell target that still satisfies the needed features and performance. — VER-01 Write for the lowest version of PowerShell that you can ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Language-Interop-and-.NET.md#ver-01-write-for-the-lowest-version-of-powershell-that-you-can)).
- Declare the supported minimum with #requires in a script or PowerShellVersion in a module manifest. — VER-02 Document the version of PowerShell the script was written for ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Language-Interop-and-.NET.md#ver-02-document-the-version-of-powershell-the-script-was-written-for)).

## Naming

- Apply PascalCase across the public API: modules, commands, types, attributes, fields, properties, global variables, constants, and parameters. — Capitalization Conventions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#capitalization-conventions)).
- Keep operator spellings and language keywords lowercase. — Capitalization Conventions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#capitalization-conventions)).
- Use uppercase for the keyword labels in comment-based help. — Capitalization Conventions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#capitalization-conventions)).
- Compose command identifiers as Verb-Noun, capitalizing each component in PascalCase. — Capitalization Conventions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#capitalization-conventions)).
- Capitalize both letters of a public two-letter acronym; ordinary words such as Id and Ok and combined acronyms follow normal casing. — Capitalization Conventions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#capitalization-conventions)).
- Optionally distinguish private variables with camelCase; qualify shared variables with their scope. — Capitalization Conventions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#capitalization-conventions)).
- A two-letter acronym at the start of a camelCase identifier begins with two lowercase letters. — Capitalization Conventions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#capitalization-conventions)).
- Name advanced functions and scripts with an approved verb and a singular noun written in PascalCase. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Spell command names completely in shared scripts rather than relying on aliases. — Use the full name of each command. ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Naming-Conventions.md#use-the-full-name-of-each-command)).
- Name parameters explicitly instead of passing arguments by position, and spell the names in full so readers can follow unfamiliar commands. — Use full parameter names. ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Naming-Conventions.md#use-full-parameter-names)).
- Use PowerShell's approved verbs within the standard Verb-Noun command pattern. — TOOL-04 Use PowerShell standard cmdlet naming ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#tool-04-use-powershell-standard-cmdlet-naming)).
- Reuse PowerShell's established parameter names for the concepts they already represent. — TOOL-05 Use PowerShell standard parameter naming ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#tool-05-use-powershell-standard-parameter-naming)).
- [unpublished TODO proposal] Provide distinct short parameter aliases for convenient interactive typing. — Specify short aliases, but don't use them ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/TODO.md#specify-short-aliases-but-dont-use-them)).
- [unpublished TODO proposal] Internal aliases may improve clarity; use established verb abbreviations in aliases that the module exports. — Provide aliases in your modules ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/TODO.md#provide-aliases-in-your-modules)).
- [unpublished TODO proposal] Create convenience aliases without replacing aliases that already exist. — Provide aliases in your modules ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/TODO.md#provide-aliases-in-your-modules)).

## Files and layout

- Isolate whitespace-only reformatting in its own commit, apart from changes to behavior. — Maintain Consistency in Layout ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#maintain-consistency-in-layout)).
- Place a statement's opening brace after its header and its closing brace first on a closing line. — One True Brace Style ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#one-true-brace-style)).
- A short scriptblock supplied to a parameter may occupy a single line. — One True Brace Style ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#one-true-brace-style)).
- Begin scripts and functions with CmdletBinding, consider accepting pipeline data, and remove lifecycle blocks that serve no purpose. — Always Start With CmdletBinding ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#always-start-with-cmdletbinding)).
- Arrange lifecycle declarations in execution order: param, begin, process, then end. — Prefer: param (), begin, process, end ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#prefer-param--begin-process-end)).
- Name lifecycle blocks explicitly instead of using an implicit end block or filter shorthand. — Prefer: param (), begin, process, end ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#prefer-param--begin-process-end)).
- Use four space characters for each indentation step; do not insert literal tabs. — Indentation ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#indentation)).
- Wrapped lines may indent farther or align with the preceding call or parameter block. — Indentation ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#indentation)).
- Prefer a 115-character line limit where practical, deferring to the project's width convention. — Maximum Line Length ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#maximum-line-length)).
- Shorten long lines through splatting or implicit continuation before considering backticks. — Maximum Line Length ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#maximum-line-length)).
- Leave two empty lines around each function or class definition. — Blank Lines and Whitespace ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#blank-lines-and-whitespace)).
- Leave one empty line around methods within a class. — Blank Lines and Whitespace ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#blank-lines-and-whitespace)).
- Adjacent related one-line definitions may share a block without intervening blank lines. — Blank Lines and Whitespace ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#blank-lines-and-whitespace)).
- Add blank lines selectively to mark meaningful groups or internal sections. — Blank Lines and Whitespace ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#blank-lines-and-whitespace)).
- Leave exactly one empty line at the end of a file. — Blank Lines and Whitespace ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#blank-lines-and-whitespace)).
- Strip whitespace from the ends of code lines. — Trailing spaces ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#trailing-spaces)).
- Separate parameter names and comparison, arithmetic, and assignment operators from surrounding tokens with one space. — Spaces around parameters and operators ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#spaces-around-parameters-and-operators)).
- Do not insert those surrounding spaces into colon-style switch arguments or unary operators. — Spaces around parameters and operators ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#spaces-around-parameters-and-operators)).
- Follow each comma or semicolon with one space. — Spaces around special characters ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#spaces-around-special-characters)).
- Space the interior of scriptblocks and subexpressions once, keeping them visually distinct from variable-delimiter braces. — Spaces around special characters ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#spaces-around-special-characters)).
- Keep ordinary parentheses and square brackets free of unnecessary interior padding. — Spaces around special characters ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#spaces-around-special-characters)).
- Preserve literal values when applying whitespace conventions. — Spaces around special characters ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#spaces-around-special-characters)).
- Leave off redundant terminating semicolons, including those after separate-line hashtable entries. — Avoid Using Semicolons (`;`) as Line Terminators ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Code-Layout-and-Formatting.md#avoid-using-semicolons--as-line-terminators)).
- Separate a simple function name from its inline parameter list with a space. — Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#functions)).
- Mark advanced functions with the CmdletBinding attribute. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Include process when any parameter binds incoming pipeline values. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Prefer full paths and anchor script-relative resources at PSScriptRoot; relative dot paths require a location explicitly established in that script or function. — Use full, explicit paths when possible. ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Naming-Conventions.md#use-full-explicit-paths-when-possible)).
- Reflect nesting depth through consistent indentation. — READ-01 Indent your code ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Readability.md#read-01-indent-your-code)).
- Prefer splatting or syntax-supported breaks; reserve a continuation backtick for cases that require it. — READ-02 Avoid backticks ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Readability.md#read-02-avoid-backticks)).
- Extract reusable work into functions and preferably organize those functions in script modules. — TOOL-02 Make your code modular ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#tool-02-make-your-code-modular)).
- Expose external facilities through an advanced function or cmdlet so callers retain a normal PowerShell interface. — PURE-04 Wrap other tools in an advanced function or cmdlet ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#pure-04-wrap-other-tools-in-an-advanced-function-or-cmdlet)).
- [rough draft] Enable CmdletBinding so standard common parameters can control and collect diagnostic streams. — Use CmdletBinding if you are using output streams ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Output-and-Formatting.md#use-cmdletbinding-if-you-are-using-output-streams)).
- Normally specify CmdletBinding to obtain common parameters and correct help behavior; only unusual advanced cases justify omitting it. — You should specify `[CmdletBinding()]` ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Writing-Parameter-Blocks.md#you-should-specify-cmdletbinding)).
- [unpublished TODO proposal] Declare assembly dependencies in RequiredAssemblies rather than loading them with Add-Type. — Use RequiredAssemblies rather than Add-Type ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/TODO.md#use-requiredassemblies-rather-than-add-type)).
- [unpublished TODO proposal] Prefer Add-Type over reflection-based assembly loading and specify full assembly names instead of LoadWithPartialName. — Use Add-Type rather than Reflection ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/TODO.md#use-add-type-rather-than-reflection)).
- [unpublished TODO proposal] Ship compiled binaries instead of embedding substantial compilations; the source's rationale is framed around PowerShell 5 security. — Prefer shipping binaries over large compilations ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/TODO.md#prefer-shipping-binaries-over-large-compilations)).
- [unpublished TODO proposal] Put .NET API usage behind PowerShell wrapper functions. — Know when to use .NET ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/TODO.md#know-when-to-use-net)).
- [unpublished TODO proposal] Group related reusable commands in modules to support isolated scope, discovery, packaging, and dependencies. — Modules ARE the Best Practice ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/TODO.md#modules-are-the-best-practice)).
- [unpublished TODO proposal] Declare module dependencies through RequiredModules. — Use RequiredModules ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/TODO.md#use-requiredmodules)).
- [unpublished TODO proposal] Save user configuration outside the installed module directory so replacing the module does not discard it. — Persisting Configuration ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/TODO.md#persisting-configuration)).

## Types and data

- Emit an object's expression directly rather than adding return merely to send that object to the pipeline. — Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#functions)).
- Produce advanced-function results during process rather than accumulating output in begin or end. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Declare OutputType for returned objects or collections, giving separate declarations for parameter sets with different result types. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Set DefaultParameterSetName as soon as any parameter declares a named set. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Express input checks with validation attributes when they can replace checks inside the implementation. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Use AllowNull when a required argument is deliberately allowed to be null. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Use AllowEmptyString when a required textual argument may contain no characters. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Use AllowEmptyCollection when a required collection argument may have zero elements. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Constrain the number of supplied elements with ValidateCount. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Constrain a text value's character count with ValidateLength. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Require a value to satisfy a regular expression through ValidatePattern. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Enforce numeric lower and upper bounds with ValidateRange. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- ValidateScript supports custom checks with the candidate in $_; returning false or throwing rejects it. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Declare permitted choices through ValidateSet. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- When a parameter must reject null, add `ValidateNotNull` if it has no type or its type admits null. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Use ValidateNotNullOrEmpty to disallow null, zero-length strings, and empty collections. — Advanced Functions ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Style-Guide/Function-Structure.md#advanced-functions)).
- Give reusable tools parameter inputs and normally return their results as pipeline objects. — TOOL-03 Make tools as re-usable as possible ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#tool-03-make-tools-as-re-usable-as-possible)).
- Return the original granular values and units from tools without presentation-oriented conversion. — TOOL-06 Tools should output raw data ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#tool-06-tools-should-output-raw-data)).
- Let controllers perform the conversions and formatting needed by their particular audience. — TOOL-07 Controllers should typically output formatted data ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Building-Reusable-Tools.md#tool-07-controllers-should-typically-output-formatted-data)).
- [rough draft] Limit Write-Host to Show/Format commands, a Formatted mode, or interactive prompting. — Don't use Write-Host unless you really mean it ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Output-and-Formatting.md#dont-use-write-host-unless-you-really-mean-it)).

- [rough draft] An internal helper may produce different result kinds when useful if its callers capture those results separately. — Two important exceptions to the single-type rule ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Output-and-Formatting.md#two-important-exceptions-to-the-single-type-rule)).

- Select a default parameter set whenever the command offers several sets. — You should pick a default ParameterSet ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Writing-Parameter-Blocks.md#you-should-pick-a-default-parameterset)).
- Declare meaningful specific parameter types so invalid input fails before the implementation uses it. — You should strongly type parameters ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Writing-Parameter-Blocks.md#you-should-strongly-type-parameters)).
- Use parameter types no broader than those accepted by downstream commands receiving the values. — You should strongly type parameters ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Writing-Parameter-Blocks.md#you-should-strongly-type-parameters)).
- Avoid string, object, and PSObject for by-value binding or distinguishing sets when their broad conversions would accept unintended inputs. — Be careful with `[string]` or `[object]` (and `[PSObject]`) ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Writing-Parameter-Blocks.md#be-careful-with-string-or-object-and-psobject)).
- If object or PSObject intentionally permits unrelated types, explicitly validate the supported types, usually through ValidateScript. — Be careful with `[string]` or `[object]` (and `[PSObject]`) ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Writing-Parameter-Blocks.md#be-careful-with-string-or-object-and-psobject)).

- Read a switch as a boolean value rather than deriving a third state from whether the caller supplied it. — Using [switch] ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Writing-Parameter-Blocks.md#using-switch)).

## Errors

- Add ErrorAction Stop to a cmdlet when its nonterminating failures must be caught as exceptions. — ERR-01 Use -ErrorAction Stop when calling cmdlets ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Error-Handling.md#err-01-use--erroraction-stop-when-calling-cmdlets)).
- For non-cmdlets, the source prescribes ErrorActionPreference Stop before execution and Continue afterward; it neither preserves a prior setting nor specifies modern native exit-code behavior. — ERR-02 Use $ErrorActionPreference = 'Stop' or 'Continue' when calling non-cmdlets ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Error-Handling.md#err-02-use-erroractionpreference--stop-or-continue-when-calling-non-cmdlets)).
- Enclose a complete dependent operation in try/catch instead of tracking success flags; recover per item when other items can proceed independently. — ERR-03 Avoid using flags to handle errors ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Error-Handling.md#err-03-avoid-using-flags-to-handle-errors)).
- Inspect exceptions or error records for diagnosis rather than inferring details from $?. — ERR-04 Avoid using $? ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Error-Handling.md#err-04-avoid-using-)).
- Prefer catching a terminating failure over interpreting a null result as failure when the operation supports trapping. — ERR-05 Avoid testing for a null variable as an error condition ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Error-Handling.md#err-05-avoid-testing-for-a-null-variable-as-an-error-condition)).
- Immediately save the caught $_ or $Error[0] in your own variable before another command can replace that context. — ERR-06 Copy $Error[0] to your own variable ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Error-Handling.md#err-06-copy-error0-to-your-own-variable)).
- Leave PowerShell's error history intact unless clearing it serves a specific purpose. — ERR-06 Copy $Error[0] to your own variable ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Error-Handling.md#err-06-copy-error0-to-your-own-variable)).

## Comments and docs

## Where the sources disagree

- Security recommends Credential for prompting from a username, while Writing Parameter Blocks says PSCredential gains this behavior automatically; check the target runtime before choosing the attribute. — Always use PSCredential for credentials/passwords ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Security.md#always-use-pscredential-for-credentialspasswords)).
- Writing Parameter Blocks says PSCredential now supplies username prompting automatically; its historical CmdletAttribute spelling conflicts with Security's Credential spelling and should not be copied as implementation guidance. — Using [pscredential] ([source](https://github.com/PoshCode/PowerShellPracticeAndStyle/blob/master/Best-Practices/Writing-Parameter-Blocks.md#using-pscredential)).

The credential-attribute disagreement above is internal to the source; this package does not silently choose between those chapters. The source also prefers any named parameter set to declare a default in Function Structure, while Writing Parameter Blocks asks for a default when several sets exist; preserve each chapter's stated scope. Its optional private-variable camelCase convention does not change public PascalCase.

Runtime clarifications: [ShouldContinue](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_functions_advanced_methods?view=powershell-7.6#shouldcontinue) adds a second confirmation after ShouldProcess, so it does not independently implement WhatIf. The source's WhatIf prose lists it as an alternative, but the example nests it within a ShouldProcess guard. This skill follows the example. The mandatory-prompt argument is [HelpMessage](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/parameter-attribute-declaration?view=powershell-7.6#parameters), not the TODO's HelpText. These clarifications do not promote the TODO proposals to guide policy.

Windows DPAPI and pre-PowerShell-5 Write-Host claims retain their historical limits. The error-preference rule reports the source's Stop/Continue sequence; it is not a claim that native exit codes automatically become terminating errors or that Continue restores a caller's previous value. Project tooling takes precedence as described in SKILL.md.
