# Strongly Encouraged Development Guidelines for PowerShell cmdlets rules (condensed)

Every Strongly Encouraged Development Guideline on the source page. These recommendations apply in context; compiled-cmdlet requirements are distinguished from script conventions.

Examples are omitted. ## Quick rules

- Keep a command's purpose focused while using parameter sets to accept reasonable alternative descriptions of its target. — Support Parameter Sets ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-parameter-sets)).
- Design a command to consume and emit pipeline data even when it is commonly placed at one end of the pipeline. — Implement for the Middle of a Pipeline ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#implement-for-the-middle-of-a-pipeline)).

## Naming

- Choose a discoverable, precise cmdlet noun, adding an abbreviated product prefix when a generic noun would collide. — Use a Specific Noun for a Cmdlet Name (SD01) ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-a-specific-noun-for-a-cmdlet-name-sd01)).
- Keep cmdlet nouns singular even for operations covering several items. — Use a Specific Noun for a Cmdlet Name (SD01) ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-a-specific-noun-for-a-cmdlet-name-sd01)).
- Pair descriptive nouns with approved verbs to make behavior predictable. — Use a Specific Noun for a Cmdlet Name (SD01) ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-a-specific-noun-for-a-cmdlet-name-sd01)).
- Capitalize each word in the command's verb and noun using PascalCase; SD02's reference to parameters is inconsistent with its heading and example. — Use Pascal Case for Cmdlet Names (SD02) ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-pascal-case-for-cmdlet-names-sd02)).
- Prefer established parameter names, adding a more specific alias when needed. — Use Standard Parameter Names ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-standard-parameter-names)).
- Keep parameter names singular when a caller may supply just one element, including array and list inputs. — Use Singular Parameter Names ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-singular-parameter-names)).
- Use a plural name only for a parameter that always requires several elements; verify the count and warn when that condition is unmet. — Use Singular Parameter Names ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-singular-parameter-names)).
- Capitalize each word of a parameter identifier, including its initial word. — Use Pascal Case for Parameter Names ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-pascal-case-for-parameter-names)).

## Files and layout

- Add useful missing members to existing output types through a product-named Types.ps1xml file. — Define ObjectMembers to Be Used as Parameters ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#define-objectmembers-to-be-used-as-parameters)).
- Provide a product-named Format.ps1xml view when the type's default rendering is inadequate. — Update Display Information ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#update-display-information)).

## Types and data

- Express a fixed set of allowed choices as an enum or a ValidateSet constraint. — Parameters That Take a List of Options ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#parameters-that-take-a-list-of-options)).
- Match a standard parameter's prescribed data type wherever it applies. — Use Standard Types for Parameters ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-standard-types-for-parameters)).
- Select a specific .NET type that validates the intended input domain. — Use Strongly-Typed .NET Framework Types ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-strongly-typed-net-framework-types)).
- Use basic strings chiefly for free-form textual input. — Use Strongly-Typed .NET Framework Types ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-strongly-typed-net-framework-types)).
- Keep the type of an equivalent parameter identical across related commands. — Use Consistent Parameter Types ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-consistent-parameter-types)).
- Represent two-state flags as SwitchParameter instead of Boolean parameters. — Parameters That Take True and False ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#parameters-that-take-true-and-false)).
- Use `Nullable<bool>` when an unchanged or unspecified state must be distinguishable from true and false. — Parameters That Take True and False ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#parameters-that-take-true-and-false)).
- Accept an array when callers reasonably need the operation repeated over several arguments. — Support Arrays for Parameters ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-arrays-for-parameters)).
- Give normally silent mutating commands a PassThru option that returns an object on request. — Support the PassThru Parameter ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-the-passthru-parameter)).
- Normally offer PassThru on commands whose verbs are Add, Set, or New. — Support the PassThru Parameter ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-the-passthru-parameter)).
- Mark no more than one parameter per set for ValueFromPipeline binding. — Support Parameter Sets ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-parameter-sets)).
- Choose the most likely interactive parameter combination as the default set. — Support Parameter Sets ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-parameter-sets)).
- Use verbose messages for optional detail about the operation being performed. — Support the WriteWarning, WriteVerbose, and WriteDebug Methods ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-the-writewarning-writeverbose-and-writedebug-methods)).
- Put diagnostic information needed by maintainers or support staff in debug output. — Support the WriteWarning, WriteVerbose, and WriteDebug Methods ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-the-writewarning-writeverbose-and-writedebug-methods)).
- For a binary cmdlet, expose parameters as public instance properties carrying the Parameter attribute; the guideline's weaker static wording is clarified by the attribute reference. — Coding Parameters (SC01) ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#coding-parameters-sc01)).
- Expose file or data-source locations through a string Path parameter with PSPath as an alias, accepting an array for multiple paths. — Support Windows PowerShell Paths ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-windows-powershell-paths)).
- Allow wildcard expansion in Path, using LiteralPath when expansion is inappropriate. — Support Windows PowerShell Paths ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-windows-powershell-paths)).
- Use provider Content access for general textual data instead of unnecessarily restricting it to files. — Support Windows PowerShell Paths ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-windows-powershell-paths)).
- Support wildcard matching for appropriate parameters that identify objects by strings. — Support Wildcard Characters ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-wildcard-characters)).
- When only one target is meaningful, still permit a wildcard but require exactly one resolved match. — Support Wildcard Characters ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-wildcard-characters)).
- Define standard members under PSStandardMembers in a custom Types.ps1xml file to integrate output types with PowerShell. — Define Standard Members ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#define-standard-members)).
- Align output member names with consuming commands' parameters to support pipeline binding. — Define ObjectMembers to Be Used as Parameters ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#define-objectmembers-to-be-used-as-parameters)).
- The source recommends implementing IComparable on every output object to support sorting and analysis; retain that broad source recommendation without treating it as a runtime requirement. — Implement the IComparable Interface ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#implement-the-icomparable-interface)).
- Include at least one pipeline-capable input in each parameter set, binding by value, by property name, or both. — Support Input from the Pipeline ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-input-from-the-pipeline)).
- Use WriteObject to emit one object; use its enumerateCollection=true overload when a collection's elements should be emitted separately. — Write Single Records to the Pipeline (SC03) ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#write-single-records-to-the-pipeline-sc03)).

## Errors

- Warn before performing work that could produce an unintended outcome. — Support the WriteWarning, WriteVerbose, and WriteDebug Methods ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-the-writewarning-writeverbose-and-writedebug-methods)).

## Comments and docs

- Provide a Help.xml file for every binary cmdlet assembly describing its commands, parameters, and usage examples; this assembly format does not replace script comment-based help. — Create a Cmdlet Help File (SD05) ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#create-a-cmdlet-help-file-sd05)).

## Performance

- Periodically report progress during lengthy work that cannot execute in the background. — Support WriteProgress for Operations that take a Long Time ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-writeprogress-for-operations-that-take-a-long-time)).
- Send each result onward when it becomes available instead of waiting to assemble a complete array. — Write Single Records to the Pipeline (SC03) ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#write-single-records-to-the-pipeline-sc03)).

## Language-specific pitfalls

- The guideline treats a nearby `WriteDebug` call as optional because it says `-Debug` also reveals verbose output. Current PowerShell controls those streams separately; include debug messages where maintainers need them. — Support the WriteWarning, WriteVerbose, and WriteDebug Methods ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-the-writewarning-writeverbose-and-writedebug-methods)).
- For necessary direct interaction beyond Write/Should methods, derive a compiled cmdlet from PSCmdlet and communicate through its Host interface. — Use the Host Interfaces ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-the-host-interfaces)).
- Keep cmdlet communication off System.Console APIs. — Use the Host Interfaces ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-the-host-interfaces)).
- Translate PowerShell provider paths with SessionState.Path before handing filesystem locations to filesystem APIs. — Support Windows PowerShell Paths ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-windows-powershell-paths)).
- Handle each arriving record in ProcessRecord when implementing a compiled cmdlet. — Support the ProcessRecord Method ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#support-the-processrecord-method)).
- Prefer case-insensitive operations while retaining the original spelling of supplied values. — Make Cmdlets Case-Insensitive and Case-Preserving (SC04) ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#make-cmdlets-case-insensitive-and-case-preserving-sc04)).

## Where the sources disagree

- Preserve host-mediated interaction unless the command intentionally provides its own GUI; this section contradictorily describes PSCmdlet.Host as both the supported route and a host bypass. — Use the Host Interfaces ([source](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/strongly-encouraged-development-guidelines#use-the-host-interfaces)).

The host contradiction above is in the original: the same property is first recommended and then described as bypassing the host. Retain host-mediated interaction and the System.Console prohibition without inventing a ban on PSCmdlet.Host. SD02's heading and command example establish command casing despite the prose saying parameter names.

Current API clarifications: [Debug](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_commonparameters?view=powershell-7.6#-debug) controls DebugPreference and [Verbose](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_commonparameters?view=powershell-7.6#-verbose) controls VerbosePreference; the old guideline's combined-stream assertion should not determine current behavior. The [Parameter attribute remarks](https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/parameter-attribute-declaration?view=powershell-7.6#remarks) require non-static parameters, prefer properties, and specify their accessors; a public static field does not satisfy that requirement. These clarifications qualify the older page rather than importing its linked required/advisory guideline collections. Project tooling takes precedence as described in SKILL.md.
