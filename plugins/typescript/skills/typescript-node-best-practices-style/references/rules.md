# Node.js Best Practices: condensed rules

Rules are grouped by topic; each line identifies the original section. Recommendations and permissions retain their source strength. Code examples are omitted.

Scope: the 2026 Node.js Best Practices edition, README snapshot `dc3d60c29d5483d9ea99cf261bbd6203516a2ba7`, plus its linked in-repository checklists. Covers every numbered item (1.1–8.15), plus linked security and Docker checklists. Performance items 7.1–7.2 remain draft guidance; historical claims are identified instead of silently adopted.

- Declare the Node version in a file read by tooling such as nvm or Volta, so developers share one version; optionally reuse it in CI and production. — [4.4 Ensure Node version is unified](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-44-ensure-node-version-is-unified).

- Use a dependency lockfile to make installed versions reproducible. — [5.4 Lock dependencies](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-54-lock-dependencies).
- Select a supervisor or orchestrator suited to keeping the service available. — [5.5 Guard process uptime using the right tool](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-55-guard-process-uptime-using-the-right-tool).
- Prepare production code with externalized state, safe caches, memory checks, named functions, CI checks, contextual logging, and orderly shutdown. — [5.9 Make your code production-ready](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-59-make-your-code-production-ready).
- Run production applications with `NODE_ENV` set to `production`. — [5.15 Set `NODE_ENV=production`](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-515-set-node_envproduction).
- Design deployment automation for atomic changes, uninterrupted service, and recovery or rollback. — [5.16 Design automated, atomic and zero-downtime deployments](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-516-design-automated-atomic-and-zero-downtime-deployments).
- Choose a supported LTS version of Node for production deployments. — [5.17 Use an LTS release of Node.js](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-517-use-an-lts-release-of-nodejs).
- Send application logs to stdout and configure routing in infrastructure rather than in application code. — [5.18 Log to stdout, avoid specifying log destination within the app](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-518-log-to-stdout-avoid-specifying-log-destination-within-the-app).
- Use `npm ci` with a lockfile that matches package metadata for repeatable installs. — [5.19 Install your packages with `npm ci`](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-519-install-your-packages-with-npm-ci).
- Launch containerized applications directly with `node` so signal delivery and child handling are explicit. — [8.2 Bootstrap using `node` command, avoid `npm start`](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-82-bootstrap-using-node-command-avoid-npm-start).
- Let the container orchestrator replicate and restart processes instead of nesting PM2 or custom cluster managers inside the container. — [8.3 Let the Docker runtime handle replication and uptime](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-83-let-the-docker-runtime-handle-replication-and-uptime).
- Pin an image version or digest instead of `latest`; use a digest when identical image content must be guaranteed. — [8.9 Use explicit image reference, avoid `latest` tag](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-89-use-explicit-image-reference-avoid-latest-tag).
- Apply the source's generic Docker checklist expanded across the relevant sections below. — [8.14 Generic Docker practices](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-814-generic-docker-practices).

- Select a maintained base image instead of performing varying base-OS updates during each build. — [sections/docker/generic-tips.md — Avoid updating the base OS](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/sections/docker/generic-tips.md#-avoid-updating-the-base-os).

## Naming

- Give functions, closures, and callbacks meaningful names for readable stack traces and profiler results. — [3.5 Name your functions](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-35-name-your-functions).
- Name classes with UpperCamelCase and routine functions, variables, and constants with lowerCamelCase; reserve UPPER_SNAKE_CASE for global/static bindings, mutable or otherwise. — [3.6 Use naming conventions for variables, constants, functions and classes](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-36-use-naming-conventions-for-variables-constants-functions-and-classes).

## Files and layout

- Organize the application around business capabilities, each with its own interface, domain behavior, and logical data ownership. — [1.1 Structure your solution by business components](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-11-structure-your-solution-by-business-components).
- Keep business components manageable and independent; they may still share a repository. — [1.1 Structure your solution by business components](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-11-structure-your-solution-by-business-components).
- Give each component separate transport/entry, business, and persistence layers. — [1.2 Layer your components with 3-tiers, keep the web layer within its boundaries](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-12-layer-your-components-with-3-tiers-keep-the-web-layer-within-its-boundaries).
- Keep HTTP framework request and response objects outside domain code. — [1.2 Layer your components with 3-tiers, keep the web layer within its boundaries](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-12-layer-your-components-with-3-tiers-keep-the-web-layer-within-its-boundaries).
- Package shared utilities independently, with package metadata and a deliberate public entry or export map. — [1.3 Wrap common utilities as packages, consider publishing](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-13-wrap-common-utilities-as-packages-consider-publishing).
- Consider workspace references or a registry for distributing shared packages; publishing requires separate task authorization. — [1.3 Wrap common utilities as packages, consider publishing](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-13-wrap-common-utilities-as-packages-consider-publishing).
- Allow environment settings to override file-based configuration. — [1.4 Use environment aware, secure and hierarchical config](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-14-use-environment-aware-secure-and-hierarchical-config).
- Choose a framework after comparing its libraries, architectural fit, and operational costs. — [1.5 Consider all the consequences when choosing the main framework](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-15-consider-all-the-consequences-when-choosing-the-main-framework).
- The source's dated framework comparison favors Nest for large OOP applications and Fastify for smaller independent components, with Express and Koa also considered; verify suitability for the actual project. — [1.5 Consider all the consequences when choosing the main framework](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-15-consider-all-the-consequences-when-choosing-the-main-framework).
- Load dependencies when the file starts rather than during ordinary function execution. — [3.8 Require modules first, not inside functions](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-38-require-modules-first-not-inside-functions).
- Expose a deliberate package or directory entry point so callers avoid private implementation paths. — [3.9 Set an explicit entry point to a module/folder](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-39-set-an-explicit-entry-point-to-a-modulefolder).
- Put effects behind explicitly called functions rather than causing them automatically during module import. — [3.13 Avoid effects outside of functions](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-313-avoid-effects-outside-of-functions).
- Prefix imports of Node built-ins with `node:`. — [6.27 Import built-in modules using the 'node:' protocol](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-627-import-built-in-modules-using-the-node-protocol).
- Use separate Docker build stages and retain only production artifacts in the final image. — [8.1 Use multi-stage builds for leaner and more secure Docker images](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-81-use-multi-stage-builds-for-leaner-and-more-secure-docker-images).
- Exclude development dependencies from production container images. — [8.5 Clean-up dependencies before production](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-85-clean-up-dependencies-before-production).
- Prefer a compact base image that still meets runtime requirements. — [8.10 Prefer smaller Docker base images](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-810-prefer-smaller-docker-base-images).
- Remove package-manager download caches from immutable production images. — [8.13 Clean NODE_MODULE cache](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-813-clean-node_module-cache).
- Prefer `COPY` for local build inputs, avoiding `ADD` unless its fetching or extraction behavior is needed. — [sections/docker/generic-tips.md — Prefer COPY over ADD command](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/sections/docker/generic-tips.md#-prefer-copy-over-add-command).

## Types and data

- Structure configuration by hierarchy, supply defaults and types, and validate it during startup. — [1.4 Use environment aware, secure and hierarchical config](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-14-use-environment-aware-secure-and-hierarchical-config).
- Favor simple TypeScript contracts, including return types, and introduce advanced typing only when a concrete need warrants it. — [1.6 Use TypeScript sparingly and thoughtfully](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-16-use-typescript-sparingly-and-thoughtfully).
- Reject invalid incoming arguments early with a suitable validation library. — [2.11 Fail fast, validate arguments using a dedicated library](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-211-fail-fast-validate-arguments-using-a-dedicated-library).
- Default to `const`, use `let` for bindings that change, and avoid `var`. — [3.7 Prefer const over let. Ditch the var](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-37-prefer-const-over-let-ditch-the-var).
- Compare values with strict equality rather than conversion-based equality. — [3.10 Use the `===` operator](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-310-use-the--operator).
- Favor async-await over callback-based asynchronous control flow. — [3.11 Use Async Await, avoid callbacks](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-311-use-async-await-avoid-callbacks).
- Favor arrow expressions for concise callbacks that retain their enclosing receiver. — [3.12 Use arrow function expressions (=>)](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-312-use-arrow-function-expressions-).
- Keep application instances stateless, moving durable or shared data to an external store. — [5.12 Strive to be stateless](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-512-strive-to-be-stateless).
- Check incoming JSON against a defined schema before using it. — [6.10 Validate incoming JSON schemas](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-610-validate-incoming-json-schemas).

## Errors

- Use promises or async-await for asynchronous failure handling instead of deeply nested error callbacks. — [2.1 Use Async-Await or promises for async error handling](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-21-use-async-await-or-promises-for-async-error-handling).
- Represent application failures consistently with subclasses of the built-in `Error`, including rejected and emitted failures. — [2.2 Extend the built-in Error object](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-22-extend-the-built-in-error-object).
- Give errors classification fields and useful codes or names so central handling can choose the right response. — [2.2 Extend the built-in Error object](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-22-extend-the-built-in-error-object).
- Separate recoverable operational problems from unknown or programming faults that require an orderly restart. — [2.3 Distinguish catastrophic errors from operational errors](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-23-distinguish-catastrophic-errors-from-operational-errors).
- Share failure logging, metrics, and restart decisions across entry points in a central handler rather than embedding them solely in HTTP middleware. — [2.4 Handle errors centrally, not within a middleware](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-24-handle-errors-centrally-not-within-a-middleware).
- On an unknown catastrophic failure, record the problem, drain connections, and exit so the runtime can restart the service. — [2.6 Exit the process gracefully when a stranger comes to town](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-26-exit-the-process-gracefully-when-a-stranger-comes-to-town).
- Use a mature structured logger for production failures instead of improvised console messages. — [2.7 Use a mature logger to increase errors visibility](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-27-use-a-mature-logger-to-increase-errors-visibility).
- Write contextual fields at useful log levels to stdout, letting infrastructure deliver the records to their destination. — [2.7 Use a mature logger to increase errors visibility](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-27-use-a-mature-logger-to-increase-errors-visibility).
- Use monitoring or APM to detect outages, failures, and slow execution in production. — [2.9 Discover errors and downtime using APM products](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-29-discover-errors-and-downtime-using-apm-products).
- Account for unhandled promise rejections centrally; the source's swallowed-error rationale is historical, because Node's default rejection mode has been `throw` since v15. — [2.10 Catch unhandled promise rejections](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-210-catch-unhandled-promise-rejections).
- Declare promise-returning functions `async` and use `return await` to preserve asynchronous stack context. — [2.12 Always await promises before returning to avoid a partial stacktrace](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-212-always-await-promises-before-returning-to-avoid-a-partial-stacktrace).
- Attach error listeners to streams and EventEmitters; a surrounding synchronous try/catch cannot catch a later emitted error. — [2.13 Subscribe to event emitters and streams 'error' event](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-213-subscribe-to-event-emitters-and-streams-error-event).
- Handle rejections from asynchronous event listeners, using `captureRejections` where appropriate. — [2.13 Subscribe to event emitters and streams 'error' event](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-213-subscribe-to-event-emitters-and-streams-error-event).
- Emit structured, searchable logs with context that makes individual events understandable. — [5.2 Increase the observability using smart logging](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-52-increase-the-observability-using-smart-logging).
- Carry correlation identifiers through service calls and attach them to related log events. — [5.14 Assign a transaction id to each log statement](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-514-assign-a-transaction-id-to-each-log-statement).
- Define fatal error categories explicitly and validate requests so routine invalid input cannot repeatedly crash the service. — [6.23 Avoid DOS attacks by explicitly setting when a process should crash](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-623-avoid-dos-attacks-by-explicitly-setting-when-a-process-should-crash).
- Raise critical alerts for exits caused by unhandled failures and catch asynchronous route failures deliberately. — [6.23 Avoid DOS attacks by explicitly setting when a process should crash](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-623-avoid-dos-attacks-by-explicitly-setting-when-a-process-should-crash).
- On SIGTERM, stop accepting traffic, drain outstanding work, and close keep-alive connections and other resources before exiting. — [8.6 Shutdown smartly and gracefully](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-86-shutdown-smartly-and-gracefully).

## Language-specific pitfalls

- Handle EventTarget listener failures at the process boundary; the source's `process.on('error')` forwarding detail is deprecated and must not become a new dependency. — [2.13 Subscribe to event emitters and streams 'error' event](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-213-subscribe-to-event-emitters-and-streams-error-event).
- Verify signal behavior for the installed npm/runtime versions; the source itself notes npm 7 forwarding changes, qualifying its older blanket claim. — [8.2 Bootstrap using `node` command, avoid `npm start`](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/README.md#-82-bootstrap-using-node-command-avoid-npm-start).
- Historical advice: the source describes certificate-key pinning and suggests considering Expect-CT first; neither is a current browser-header recommendation. — [sections/security/secureheaders.md — Public Key Pinning for HTTP (HPKP)](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/sections/security/secureheaders.md#public-key-pinning-for-http-hpkp).
- Historical advice: the source configures `X-XSS-Protection` browser filtering; current guidance avoids enabling that obsolete filter. — [sections/security/secureheaders.md — X-XSS-Protection](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/sections/security/secureheaders.md#x-xss-protection).
- Historical advice: the source uses Expect-CT to request certificate-transparency reporting or enforcement; this obsolete header is not a current deployment recommendation. — [sections/security/secureheaders.md — Expect-CT](https://github.com/goldbergyoni/nodebestpractices/blob/dc3d60c29d5483d9ea99cf261bbd6203516a2ba7/sections/security/secureheaders.md#expect-ct).

## Where the sources disagree

This source permits either safe semicolon convention, favors arrow expressions while asking for named callbacks, and uses uppercase names for global/static bindings even when mutable. Keep those choices when this source is selected; assign descriptive bindings to arrow callbacks when needed. Treat operational errors as recoverable and unknown programmer failures as restart-worthy.

Historical qualifications were checked against [Node rejection modes](https://nodejs.org/api/cli.html#--unhandled-rejectionsmode), [EventTarget error handling](https://nodejs.org/api/events.html#eventtarget-error-handling), [OWASP password guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#implement-proper-password-strength-controls), [OWASP HTTP-header guidance](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html), and [MDN framing directives](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Frame-Options#directives). Those references qualify the old claims; their text is not reproduced here.
