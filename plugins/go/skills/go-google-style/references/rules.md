# Google Go rules

Condensed Google Go Guide, Decisions, and Best Practices. The Guide takes precedence over Decisions; Best Practices is advisory. Internal build, logging, and review procedures are omitted.

Source owner: Google. License: [CC-BY-3.0](../LICENSE). Changes by style-skills contributors: rules restated and shortened, examples omitted, source-local rules removed, and scope/version clarifications identified. Unofficial; no endorsement is implied.

## Quick rules

Read the topic sections below; each retained source rule appears once.

## Tooling

- Format every Go file with gofmt. — [Google: guide: Formatting](https://google.github.io/styleguide/go/guide#formatting). <!-- google-go-style:33 -->
- Normally apply formatting to generated files too. — [Google: guide: Formatting](https://google.github.io/styleguide/go/guide#formatting). <!-- google-go-style:34 -->
- Leave source width free of a fixed column maximum. — [Google: guide: Line length](https://google.github.io/styleguide/go/guide#line-length). <!-- google-go-style:39 -->
- Align a multiline literal's closing brace with the line that opened it. — [Google: decisions: Literal formatting](https://google.github.io/styleguide/go/decisions#literal-formatting). <!-- google-go-style:149 -->
- Put a trailing comma after the last multiline element and close the literal on a new line. — [Google: decisions: Literal formatting](https://google.github.io/styleguide/go/decisions#literal-formatting). <!-- google-go-style:150 -->
- For slice and array literals, combine adjacent braces only at matching indentation when the inner expressions are literals or proto builders. — [Google: decisions: Literal formatting](https://google.github.io/styleguide/go/decisions#literal-formatting). <!-- google-go-style:151 -->
- If such wrapping is unavoidable, add an empty line between the header and body. — [Google: decisions: Indentation confusion](https://google.github.io/styleguide/go/decisions#indentation-confusion). <!-- google-go-style:160 -->
- Keep each declared function or method signature on one line. — [Google: decisions: Function formatting](https://google.github.io/styleguide/go/decisions#func-formatting). <!-- google-go-style:161 -->
- Do not split function calls purely to reduce line width. — [Google: decisions: Function formatting](https://google.github.io/styleguide/go/decisions#func-formatting). <!-- google-go-style:162 -->
- Do not wrap ordinary control headers only to shorten them. — [Google: decisions: Conditionals and loops](https://google.github.io/styleguide/go/decisions#conditional-formatting). <!-- google-go-style:167 -->
- Make brace pairing clear in conditions containing closures or multiline literals. — [Google: decisions: Conditionals and loops](https://google.github.io/styleguide/go/decisions#conditional-formatting). <!-- google-go-style:169 -->
- For a multiline case list, use consistent indentation and an empty line before the body. — [Google: decisions: Conditionals and loops](https://google.github.io/styleguide/go/decisions#conditional-formatting). <!-- google-go-style:170 -->
- Prefer the subcommands library when it meets the CLI's needs and other considerations are equal. — [Google: best-practices: Complex command-line interfaces](https://google.github.io/styleguide/go/best-practices#complex-clis). <!-- google-go-style:447 -->
- Choose a more capable CLI library when its additional features are actually needed. — [Google: best-practices: Complex command-line interfaces](https://google.github.io/styleguide/go/best-practices#complex-clis). <!-- google-go-style:448 -->

## Naming

- Use snake_case for flag names and mixedCaps for the associated Go variables. — [Google — flags](https://google.github.io/styleguide/go/decisions#flags).

- Give generated protocol-buffer package aliases a `pb` suffix. — [Google — import renaming](https://google.github.io/styleguide/go/decisions#import-renaming).

- Use predictable names consistently for equivalent concepts. — [Google: guide: Maintainability](https://google.github.io/styleguide/go/guide#maintainability). <!-- google-go-style:28 -->
- Use mixed capitalization, not underscore-separated words, in multiword identifiers. — [Google: guide: MixedCaps](https://google.github.io/styleguide/go/guide#mixed-caps). <!-- google-go-style:36 -->
- Apply mixed capitalization to constants too, using the first letter to control export visibility. — [Google: guide: MixedCaps](https://google.github.io/styleguide/go/guide#mixed-caps). <!-- google-go-style:37 -->
- Begin local identifiers with lowercase because they are unexported. — [Google: guide: MixedCaps](https://google.github.io/styleguide/go/guide#mixed-caps). <!-- google-go-style:38 -->
- Normally keep underscores out of Go identifiers. — [Google: decisions: Underscores](https://google.github.io/styleguide/go/decisions#underscores). <!-- google-go-style:50 -->
- Allow the documented underscore exceptions for generated-only packages, testing function names, and rare OS or cgo interoperability. — [Google: decisions: Underscores](https://google.github.io/styleguide/go/decisions#underscores). <!-- google-go-style:51 -->
- Use compact lowercase alphanumeric package names with no separators between words. — [Google: decisions: Package names](https://google.github.io/styleguide/go/decisions#package-names). <!-- google-go-style:53 -->
- Avoid package names that clients will routinely need as local variable names. — [Google: decisions: Package names](https://google.github.io/styleguide/go/decisions#package-names). <!-- google-go-style:54 -->
- The documented underscore exceptions also cover functional or integration test packages and package-level examples. — [Google: decisions: Package names](https://google.github.io/styleguide/go/decisions#package-names). <!-- google-go-style:57 -->
- Avoid vague catch-all package identifiers that do not explain the package's job. — [Google: decisions: Package names](https://google.github.io/styleguide/go/decisions#package-names). <!-- google-go-style:58 -->
- Name a receiver with a brief abbreviation of its type, usually one or two letters. — [Google: decisions: Receiver names](https://google.github.io/styleguide/go/decisions#receiver-names). <!-- google-go-style:60 -->
- Reuse the same receiver identifier across a type's methods. — [Google: decisions: Receiver names](https://google.github.io/styleguide/go/decisions#receiver-names). <!-- google-go-style:61 -->
- Omit an unused receiver's name instead of naming it _. — [Google: decisions: Receiver names](https://google.github.io/styleguide/go/decisions#receiver-names). <!-- google-go-style:62 -->
- Use mixed capitalization for constants without an uppercase-underscore style or K prefix. — [Google: decisions: Constant names](https://google.github.io/styleguide/go/decisions#constant-names). <!-- google-go-style:63 -->
- Name constants for what they mean rather than spelling their literal contents. — [Google: decisions: Constant names](https://google.github.io/styleguide/go/decisions#constant-names). <!-- google-go-style:64 -->
- Keep each initialism's conventional capitalization internally consistent. — [Google: decisions: Initialisms](https://google.github.io/styleguide/go/decisions#initialisms). <!-- google-go-style:66 -->
- Adjacent initialisms may use different casing from one another if each is internally consistent. — [Google: decisions: Initialisms](https://google.github.io/styleguide/go/decisions#initialisms). <!-- google-go-style:67 -->
- Retain an initialism's customary mixed case unless export visibility requires normalizing the whole abbreviation. — [Google: decisions: Initialisms](https://google.github.io/styleguide/go/decisions#initialisms). <!-- google-go-style:68 -->
- Use familiar abbreviations in their normal prose form, including ID and DB. — [Google: decisions: Initialisms](https://google.github.io/styleguide/go/decisions#initialisms). <!-- google-go-style:69 -->
- Give ordinary accessors noun names without Get. — [Google: decisions: Getters](https://google.github.io/styleguide/go/decisions#getters). <!-- google-go-style:70 -->
- Retain Get when it names the actual domain operation. — [Google: decisions: Getters](https://google.github.io/styleguide/go/decisions#getters). <!-- google-go-style:71 -->
- Signal expensive, blocking, or fallible retrieval through an appropriate action verb. — [Google: decisions: Getters](https://google.github.io/styleguide/go/decisions#getters). <!-- google-go-style:72 -->
- Increase name detail with scope and the number of competing concepts. — [Google: decisions: Variable names](https://google.github.io/styleguide/go/decisions#variable-names). <!-- google-go-style:73 -->
- Name a local value for its current role instead of its source field or originating system. — [Google: decisions: Variable names](https://google.github.io/styleguide/go/decisions#variable-names). <!-- google-go-style:74 -->
- Start with one clear word and add qualifiers only to distinguish similar values. — [Google: decisions: Variable names](https://google.github.io/styleguide/go/decisions#variable-names). <!-- google-go-style:75 -->
- Avoid improvised abbreviations formed by stripping letters out of words. — [Google: decisions: Variable names](https://google.github.io/styleguide/go/decisions#variable-names). <!-- google-go-style:76 -->
- Usually omit type names and redundant context from variable identifiers. — [Google: decisions: Variable names](https://google.github.io/styleguide/go/decisions#variable-names). <!-- google-go-style:77 -->
- Use representation qualifiers when one value appears simultaneously in different forms. — [Google: decisions: Variable names](https://google.github.io/styleguide/go/decisions#variable-names). <!-- google-go-style:78 -->
- Reserve single-letter identifiers for short scopes or unmistakable conventional roles. — [Google: decisions: Variable names](https://google.github.io/styleguide/go/decisions#variable-names). <!-- google-go-style:79 -->
- Use conventional brief names for readers, writers, receivers, indices, and coordinates when clear. — [Google: decisions: Variable names](https://google.github.io/styleguide/go/decisions#variable-names). <!-- google-go-style:80 -->
- Do not repeat the package qualifier inside an exported identifier. — [Google: decisions: Repetition](https://google.github.io/styleguide/go/decisions#repetition). <!-- google-go-style:82 -->
- Use New for the only constructor type already named by its package. — [Google: decisions: Repetition](https://google.github.io/styleguide/go/decisions#repetition). <!-- google-go-style:83 -->
- Include a variable's type in its name only when concurrent representations require disambiguation. — [Google: decisions: Repetition](https://google.github.io/styleguide/go/decisions#repetition). <!-- google-go-style:84 -->
- Judge a name in its full usage context, including enclosing package, type, function, and file. — [Google: decisions: Repetition](https://google.github.io/styleguide/go/decisions#repetition). <!-- google-go-style:85 -->
- Name results to distinguish equal-typed values or make required caller actions apparent. — [Google: decisions: Named result parameters](https://google.github.io/styleguide/go/decisions#named-result-parameters). <!-- google-go-style:105 -->
- Omit result names that restate what the function or type already communicates. — [Google: decisions: Named result parameters](https://google.github.io/styleguide/go/decisions#named-result-parameters). <!-- google-go-style:106 -->
- Do not name results merely to save a declaration or permit naked returns. — [Google: decisions: Named result parameters](https://google.github.io/styleguide/go/decisions#named-result-parameters). <!-- google-go-style:107 -->
- Use a pkg suffix to distinguish an import from a useful same-named local variable. — [Google: decisions: Import renaming](https://google.github.io/styleguide/go/decisions#import-renaming). <!-- google-go-style:122 -->
- Prefix failure-terminating setup helpers with Must or must. — [Google: decisions: Must functions](https://google.github.io/styleguide/go/decisions#must-functions). <!-- google-go-style:179 -->
- Include the package name in an unavoidable library flag's name. — [Google: decisions: Flags](https://google.github.io/styleguide/go/decisions#flags). <!-- google-go-style:229 -->
- Prefer the diagnostic terms got and want. — [Google: decisions: Got before want](https://google.github.io/styleguide/go/decisions#got-before-want). <!-- google-go-style:256 -->
- Choose informative subtest names that stay readable after escaping and are convenient in filters. — [Google: decisions: Subtest names](https://google.github.io/styleguide/go/decisions#subtest-names). <!-- google-go-style:290 -->
- Avoid whitespace, control characters, and especially slashes in subtest names. — [Google: decisions: Subtest names](https://google.github.io/styleguide/go/decisions#subtest-names). <!-- google-go-style:291 -->
- Leave types, receiver details, and pointer status out of function names unless they distinguish alternatives. — [Google: best-practices: Function and method names](https://google.github.io/styleguide/go/best-practices#function-name-repetition). <!-- google-go-style:312 -->
- Do not repeat a package qualifier in function names or a receiver type in method names. — [Google: best-practices: Function and method names](https://google.github.io/styleguide/go/best-practices#function-name-repetition). <!-- google-go-style:313 -->
- Avoid restating parameter or result identifiers inside a function's name. — [Google: best-practices: Function and method names](https://google.github.io/styleguide/go/best-practices#function-name-repetition). <!-- google-go-style:314 -->
- Add qualifiers only when they distinguish otherwise similar operations. — [Google: best-practices: Function and method names](https://google.github.io/styleguide/go/best-practices#function-name-repetition). <!-- google-go-style:315 -->
- Prefer noun-like function names when returning a value is the main purpose. — [Google: best-practices: Naming conventions](https://google.github.io/styleguide/go/best-practices#function-name-conventions). <!-- google-go-style:316 -->
- Prefer action verbs for functions whose main purpose is doing work. — [Google: best-practices: Naming conventions](https://google.github.io/styleguide/go/best-practices#function-name-conventions). <!-- google-go-style:317 -->
- Suffix equivalent typed operations with the distinguishing type name. — [Google: best-practices: Naming conventions](https://google.github.io/styleguide/go/best-practices#function-name-conventions). <!-- google-go-style:318 -->
- The principal operation may omit a type suffix when alternatives stay unambiguous. — [Google: best-practices: Naming conventions](https://google.github.io/styleguide/go/best-practices#function-name-conventions). <!-- google-go-style:319 -->
- A helper package may take the production package's name with test appended. — [Google: best-practices: Test double and helper packages](https://google.github.io/styleguide/go/best-practices#naming-doubles). <!-- google-go-style:320 -->
- Use a short double name within a testing package when it doubles only one type. — [Google: best-practices: Test double and helper packages](https://google.github.io/styleguide/go/best-practices#naming-doubles). <!-- google-go-style:321 -->
- Name behavioral variants of test doubles for their behavior. — [Google: best-practices: Test double and helper packages](https://google.github.io/styleguide/go/best-practices#naming-doubles). <!-- google-go-style:322 -->
- Include the subject type when a testing package contains doubles for several types. — [Google: best-practices: Test double and helper packages](https://google.github.io/styleguide/go/best-practices#naming-doubles). <!-- google-go-style:323 -->
- Name local doubles so they are easy to distinguish from actual production values. — [Google: best-practices: Test double and helper packages](https://google.github.io/styleguide/go/best-practices#naming-doubles). <!-- google-go-style:324 -->
- Prefer a distinct name to deliberate shadowing when it improves readability. — [Google: best-practices: Shadowing](https://google.github.io/styleguide/go/best-practices#shadowing). <!-- google-go-style:328 -->
- Avoid shadowing standard-library package names beyond very small scopes. — [Google: best-practices: Shadowing](https://google.github.io/styleguide/go/best-practices#shadowing). <!-- google-go-style:329 -->
- Do not choose package names that clients will routinely need for useful local values. — [Google: best-practices: Shadowing](https://google.github.io/styleguide/go/best-practices#shadowing). <!-- google-go-style:330 -->
- Name a package for the capabilities it supplies. — [Google: best-practices: Util packages](https://google.github.io/styleguide/go/best-practices#util-packages). <!-- google-go-style:331 -->
- Avoid a generic utility or helper label as a package's entire name. — [Google: best-practices: Util packages](https://google.github.io/styleguide/go/best-practices#util-packages). <!-- google-go-style:332 -->
- Assess package names together with their qualified call sites. — [Google: best-practices: Util packages](https://google.github.io/styleguide/go/best-practices#util-packages). <!-- google-go-style:333 -->
- Use descriptive words rather than cryptic abbreviations in generated-code import aliases. — [Google: best-practices: Protocol Buffer Messages and Stubs](https://google.github.io/styleguide/go/best-practices#import-protos). <!-- google-go-style:346 -->
- Do not perpetuate old extremely short protobuf import aliases in new code. — [Google: best-practices: Protocol Buffer Messages and Stubs](https://google.github.io/styleguide/go/best-practices#import-protos). <!-- google-go-style:347 -->

## Files and layout

- If an existing deviation cannot be corrected within the change, track the follow-up separately rather than expanding the current edit. — [Google — Local consistency](https://google.github.io/styleguide/go/guide#local-consistency).

- Do not use dot imports, including in tests, under Google’s style. — [Google — import dot](https://google.github.io/styleguide/go/decisions#import-dot).

- Group imports in this order: standard library, other packages, generated protos, then side-effect imports. — [Google — import grouping](https://google.github.io/styleguide/go/decisions#import-grouping).

- Use an adequate standard-library solution before adding an external dependency. — [Google: guide: Least mechanism](https://google.github.io/styleguide/go/guide#least-mechanism). <!-- google-go-style:14 -->
- Limit dependencies, particularly reliance on undocumented implementation behavior. — [Google: guide: Maintainability](https://google.github.io/styleguide/go/guide#maintainability). <!-- google-go-style:29 -->
- Underscores are permitted in source filenames. — [Google: decisions: Underscores](https://google.github.io/styleguide/go/decisions#underscores). <!-- google-go-style:52 -->
- Alias an underscore-containing package name to an idiomatic local name. — [Google: decisions: Package names](https://google.github.io/styleguide/go/decisions#package-names). <!-- google-go-style:55 -->
- Name an external unit-test package by appending _test to the tested package's name. — [Google: decisions: Package names](https://google.github.io/styleguide/go/decisions#package-names). <!-- google-go-style:56 -->
- Give import aliases ordinary package-style names and use them consistently nearby. — [Google: decisions: Package names](https://google.github.io/styleguide/go/decisions#package-names). <!-- google-go-style:59 -->
- A doc.go file containing just package documentation and its clause is acceptable. — [Google: decisions: Package comments](https://google.github.io/styleguide/go/decisions#package-comments). <!-- google-go-style:114 -->
- Keep normal import names instead of routinely aliasing them. — [Google: decisions: Import renaming](https://google.github.io/styleguide/go/decisions#import-renaming). <!-- google-go-style:117 -->
- When import names collide, prefer aliasing the more local package. — [Google: decisions: Import renaming](https://google.github.io/styleguide/go/decisions#import-renaming). <!-- google-go-style:118 -->
- Use consistent lowercase aliases without underscores. — [Google: decisions: Import renaming](https://google.github.io/styleguide/go/decisions#import-renaming). <!-- google-go-style:119 -->
- Rename a vague imported package only for a material readability gain; improve its own name when possible. — [Google: decisions: Import renaming](https://google.github.io/styleguide/go/decisions#import-renaming). <!-- google-go-style:121 -->
- Use side-effect imports only in main or in tests that require them. — [Google: decisions: Import blank](https://google.github.io/styleguide/go/decisions#import-blank). <!-- google-go-style:124 -->
- Do not force initialization-only imports through ordinary reusable libraries. — [Google: decisions: Import blank](https://google.github.io/styleguide/go/decisions#import-blank). <!-- google-go-style:125 -->
- Blank-import embed when a go:embed directive requires the package but no identifier. — [Google: decisions: Import blank](https://google.github.io/styleguide/go/decisions#import-blank). <!-- google-go-style:127 -->
- Define command-line flags in main or its equivalent entrypoint. — [Google: decisions: Flags](https://google.github.io/styleguide/go/decisions#flags). <!-- google-go-style:227 -->
- Place grouped global flag declarations directly below the imports. — [Google: decisions: Flags](https://google.github.io/styleguide/go/decisions#flags). <!-- google-go-style:230 -->
- Use the original package clause in same-package _test.go files without importing that package again. — [Google: decisions: Test package](https://google.github.io/styleguide/go/decisions#test-package). <!-- google-go-style:303 -->
- Use an external _test package when integration testing or dependency cycles require it. — [Google: decisions: Test package](https://google.github.io/styleguide/go/decisions#test-package). <!-- google-go-style:304 -->
- Keep cooperating public types together when clients usually use them as a group. — [Google: best-practices: Package size](https://google.github.io/styleguide/go/best-practices#package-size). <!-- google-go-style:334 -->
- Keep coupled implementation types together to avoid exposing their internals between packages. — [Google: best-practices: Package size](https://google.github.io/styleguide/go/best-practices#package-size). <!-- google-go-style:335 -->
- Combine packages if users cannot usefully depend on one without the other. — [Google: best-practices: Package size](https://google.github.io/styleguide/go/best-practices#package-size). <!-- google-go-style:336 -->
- Give an independent concept a focused package of its own. — [Google: best-practices: Package size](https://google.github.io/styleguide/go/best-practices#package-size). <!-- google-go-style:337 -->
- Avoid collecting a whole project into an oversized package. — [Google: best-practices: Package size](https://google.github.io/styleguide/go/best-practices#package-size). <!-- google-go-style:338 -->
- Divide related code into files whose organization maintainers can predict. — [Google: best-practices: Package size](https://google.github.io/styleguide/go/best-practices#package-size). <!-- google-go-style:339 -->
- Avoid both enormous files and needless proliferation of tiny files. — [Google: best-practices: Package size](https://google.github.io/styleguide/go/best-practices#package-size). <!-- google-go-style:340 -->
- Do not require each type to have a separate file. — [Google: best-practices: Package size](https://google.github.io/styleguide/go/best-practices#package-size). <!-- google-go-style:341 -->
- A separate doc.go can hold long package documentation but is optional. — [Google: best-practices: Package size](https://google.github.io/styleguide/go/best-practices#package-size). <!-- google-go-style:342 -->
- Prefer one package per directory when preparing a Bazel project for public reuse. — [Google: best-practices: Package size](https://google.github.io/styleguide/go/best-practices#package-size). <!-- google-go-style:344 -->
- Do not rename existing short aliases solely because the recommendation has changed. — [Google: best-practices: Protocol Buffer Messages and Stubs](https://google.github.io/styleguide/go/best-practices#import-protos). <!-- google-go-style:348 -->
- Do not require a separate package for every subcommand. — [Google: best-practices: Complex command-line interfaces](https://google.github.io/styleguide/go/best-practices#complex-clis). <!-- google-go-style:450 -->
- Separate reusable library behavior from its command-line frontend when both are needed. — [Google: best-practices: Complex command-line interfaces](https://google.github.io/styleguide/go/best-practices#complex-clis). <!-- google-go-style:451 -->
- An interface can break a dependency cycle, but first consider merging the involved packages. — [Google: best-practices: Avoid unnecessary interfaces](https://google.github.io/styleguide/go/best-practices#avoid-unnecessary-interfaces). <!-- google-go-style:515 -->
- A separate protocol package can avoid dependencies on large implementations or dependency cycles. — [Google: best-practices: Interface ownership and visibility](https://google.github.io/styleguide/go/best-practices#interface-ownership-and-visibility). <!-- google-go-style:519 -->
- An interface result can resolve a cycle, but reconsider package boundaries before choosing that fix. — [Google: best-practices: Designing effective interfaces](https://google.github.io/styleguide/go/best-practices#designing-effective-interfaces). <!-- google-go-style:529 -->

## Types and data

- Remove cleverness and abstraction that deliver no specific benefit. — [Google: guide: Simplicity](https://google.github.io/styleguide/go/guide#simplicity). <!-- google-go-style:9 -->
- Introduce necessary complexity intentionally and support its use with rationale, examples, and tests. — [Google: guide: Simplicity](https://google.github.io/styleguide/go/guide#simplicity). <!-- google-go-style:11 -->
- Use a sufficient language construct before reaching for a library abstraction. — [Google: guide: Least mechanism](https://google.github.io/styleguide/go/guide#least-mechanism). <!-- google-go-style:13 -->
- A boolean map may be the clearest solution for basic membership checks. — [Google: guide: Least mechanism](https://google.github.io/styleguide/go/guide#least-mechanism). <!-- google-go-style:17 -->
- Choose APIs that can evolve without imposing awkward client changes. — [Google: guide: Maintainability](https://google.github.io/styleguide/go/guide#maintainability). <!-- google-go-style:22 -->
- Expose assumptions and model abstractions on the application's concepts. — [Google: guide: Maintainability](https://google.github.io/styleguide/go/guide#maintainability). <!-- google-go-style:23 -->
- Remove unused capabilities and avoidable dependencies between components. — [Google: guide: Maintainability](https://google.github.io/styleguide/go/guide#maintainability). <!-- google-go-style:24 -->
- Require an abstraction's benefits to outweigh the implementation context it hides. — [Google: guide: Maintainability](https://google.github.io/styleguide/go/guide#maintainability). <!-- google-go-style:26 -->
- Accept modest initial complexity when it enables safer future changes. — [Google: guide: Maintainability](https://google.github.io/styleguide/go/guide#maintainability). <!-- google-go-style:30 -->
- Keep long string literals intact instead of splitting them to meet a column target. — [Google: guide: Line length](https://google.github.io/styleguide/go/guide#line-length). <!-- google-go-style:43 -->
- Do not create a constant name with no significance beyond the literal itself. — [Google: decisions: Constant names](https://google.github.io/styleguide/go/decisions#constant-names). <!-- google-go-style:65 -->
- A deferred update is a valid reason to name a return value. — [Google: decisions: Named result parameters](https://google.github.io/styleguide/go/decisions#named-result-parameters). <!-- google-go-style:109 -->
- Prefer composite initialization to repeated assignments of individual fields. — [Google: decisions: Literal formatting](https://google.github.io/styleguide/go/decisions#literal-formatting). <!-- google-go-style:146 -->
- Use keyed literals for structs belonging to other packages. — [Google: decisions: Literal formatting](https://google.github.io/styleguide/go/decisions#literal-formatting). <!-- google-go-style:147 -->
