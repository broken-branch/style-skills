# Rust API Guidelines: condensed rules

API recommendations retain their advisory scope. Old API examples such as `try!` do not establish a compiler minimum.

Source owner: The Rust Project Developers. License: [MIT OR Apache-2.0](../LICENSE). Changes: rules independently restated, shortened and grouped by topic; examples omitted. Unofficial; no endorsement is implied.

## Naming

- Use `UpperCamelCase` for type, trait, and enum-variant names. — [Rust API Guidelines: Casing conforms to RFC 430 (C-CASE)](https://rust-lang.github.io/api-guidelines/naming.html#c-case). <!-- API:001 -->
- Use `snake_case` for module, function, method, local-variable, and macro names. — [Rust API Guidelines: Casing conforms to RFC 430 (C-CASE)](https://rust-lang.github.io/api-guidelines/naming.html#c-case). <!-- API:002 -->
- Name constants and statics with `SCREAMING_SNAKE_CASE`. — [Rust API Guidelines: Casing conforms to RFC 430 (C-CASE)](https://rust-lang.github.io/api-guidelines/naming.html#c-case). <!-- API:003 -->
- Keep generic type names brief, often one uppercase letter, and lifetimes brief and lowercase. — [Rust API Guidelines: Casing conforms to RFC 430 (C-CASE)](https://rust-lang.github.io/api-guidelines/naming.html#c-case). <!-- API:004 -->
- Capitalize acronyms as words in CamelCase and use lowercase acronym text in snake_case. — [Rust API Guidelines: Casing conforms to RFC 430 (C-CASE)](https://rust-lang.github.io/api-guidelines/naming.html#c-case). <!-- API:005 -->
- Avoid single-letter components in snake_case names unless they are the last component. — [Rust API Guidelines: Casing conforms to RFC 430 (C-CASE)](https://rust-lang.github.io/api-guidelines/naming.html#c-case). <!-- API:006 -->
- Leave `rust` and `rs` decorations off crate-name beginnings and endings. — [Rust API Guidelines: Casing conforms to RFC 430 (C-CASE)](https://rust-lang.github.io/api-guidelines/naming.html#c-case). <!-- API:007 -->
- Make ad hoc conversions methods on their source or destination type. — [Rust API Guidelines: Ad-hoc conversions follow as_, to_, into_ conventions (C-CONV)](https://rust-lang.github.io/api-guidelines/naming.html#c-conv). <!-- API:008 -->
- Name cheap borrowed views `as_`, working or copying conversions `to_`, and ownership-consuming non-`Copy` conversions `into_`. — [Rust API Guidelines: Ad-hoc conversions follow as_, to_, into_ conventions (C-CONV)](https://rust-lang.github.io/api-guidelines/naming.html#c-conv). <!-- API:009 -->
- Call extraction of a wrapper's underlying representation `into_inner`. — [Rust API Guidelines: Ad-hoc conversions follow as_, to_, into_ conventions (C-CONV)](https://rust-lang.github.io/api-guidelines/naming.html#c-conv). <!-- API:010 -->
- Place `mut` within a conversion name in the same position as in its result type. — [Rust API Guidelines: Ad-hoc conversions follow as_, to_, into_ conventions (C-CONV)](https://rust-lang.github.io/api-guidelines/naming.html#c-conv). <!-- API:011 -->
- Usually name field accessors directly, without `get_`. — [Rust API Guidelines: Getter names follow Rust convention (C-GETTER)](https://rust-lang.github.io/api-guidelines/naming.html#c-getter). <!-- API:012 -->
- Use `get` when there is one unambiguous value to retrieve. — [Rust API Guidelines: Getter names follow Rust convention (C-GETTER)](https://rust-lang.github.io/api-guidelines/naming.html#c-getter). <!-- API:013 -->
- For homogeneous collections, use `iter`, `iter_mut`, and `into_iter` for shared, mutable, and owned iteration respectively. — [Rust API Guidelines: Methods on collections that produce iterators follow iter, iter_mut, into_iter (C-ITER)](https://rust-lang.github.io/api-guidelines/naming.html#c-iter). <!-- API:015 -->
- Do not force collection iteration names onto free functions or values with several meaningful interpretations, such as text. — [Rust API Guidelines: Methods on collections that produce iterators follow iter, iter_mut, into_iter (C-ITER)](https://rust-lang.github.io/api-guidelines/naming.html#c-iter). <!-- API:016 -->
- Derive iterator type names from their producing methods, relying on module paths to distinguish context. — [Rust API Guidelines: Iterator type names match the methods that produce them (C-ITER-TY)](https://rust-lang.github.io/api-guidelines/naming.html#c-iter-ty). <!-- API:017 -->
- Name features for capabilities, without filler such as `use-` or `with-`. — [Rust API Guidelines: Feature names are free of placeholder words (C-FEATURE)](https://rust-lang.github.io/api-guidelines/naming.html#c-feature). <!-- API:018 -->
- Call optional integrations with the standard library and Serde `std` and `serde` respectively. — [Rust API Guidelines: Feature names are free of placeholder words (C-FEATURE)](https://rust-lang.github.io/api-guidelines/naming.html#c-feature). <!-- API:019 -->
- Keep word ordering consistent within an API family and with analogous standard APIs. — [Rust API Guidelines: Names use a consistent word order (C-WORD-ORDER)](https://rust-lang.github.io/api-guidelines/naming.html#c-word-order). <!-- API:021 -->
- When either direction is equally appropriate, prefer chainable `to_`, `as_`, or `into_` conversions over `from_` functions. — [Rust API Guidelines: Conversions live on the most specific type involved (C-CONV-SPECIFIC)](https://rust-lang.github.io/api-guidelines/predictability.html#c-conv-specific). <!-- API:068 -->
- Usually call the main constructor `new`, allowing domain-specific acquisition verbs where appropriate. — [Rust API Guidelines: Constructors are static, inherent methods (C-CTOR)](https://rust-lang.github.io/api-guidelines/predictability.html#c-ctor). <!-- API:076 -->
- Give secondary constructors descriptive `with` names, switching to a builder when configuration grows. — [Rust API Guidelines: Constructors are static, inherent methods (C-CTOR)](https://rust-lang.github.io/api-guidelines/predictability.html#c-ctor). <!-- API:077 -->
- Use named `from_` construction for unsafe conversions, additional arguments, or explicit interpretation of raw input. — [Rust API Guidelines: Constructors are static, inherent methods (C-CTOR)](https://rust-lang.github.io/api-guidelines/predictability.html#c-ctor). <!-- API:078 -->
- Mark validation-bypassing APIs with an `unchecked` suffix or a `raw` module boundary. — [Rust API Guidelines: Functions validate their arguments (C-VALIDATE)](https://rust-lang.github.io/api-guidelines/dependability.html#c-validate). <!-- API:100 -->

## Files and layout

- Keep features additive and their names positive rather than negated. — [Rust API Guidelines: Feature names are free of placeholder words (C-FEATURE)](https://rust-lang.github.io/api-guidelines/naming.html#c-feature). <!-- API:020 -->
- If Serde is not otherwise needed, expose it through an optional `serde` feature. — [Rust API Guidelines: Data structures implement Serde's Serialize, Deserialize (C-SERDE)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-serde). <!-- API:029 -->
- Populate package authors, description, license, repository, keywords, and categories. — [Rust API Guidelines: Cargo.toml includes all common metadata (C-METADATA)](https://rust-lang.github.io/api-guidelines/documentation.html#c-metadata). <!-- API:059 -->
- Set a package's `documentation` URL only when hosting differs from docs.rs. — [Rust API Guidelines: Cargo.toml includes all common metadata (C-METADATA)](https://rust-lang.github.io/api-guidelines/documentation.html#c-metadata). <!-- API:060 -->
- Use `homepage` only for a separate project site, without repeating repository or API-doc URLs. — [Rust API Guidelines: Cargo.toml includes all common metadata (C-METADATA)](https://rust-lang.github.io/api-guidelines/documentation.html#c-metadata). <!-- API:061 -->
- When publishing a release, tag its source commit, preferably with an annotated tag. — [Rust API Guidelines: Release notes document all significant changes (C-RELNOTES)](https://rust-lang.github.io/api-guidelines/documentation.html#c-relnotes). <!-- API:064 -->
- For broad ecosystem compatibility, prefer `MIT OR Apache-2.0` or similarly compatible permissive terms. — [Rust API Guidelines: Crate and its dependencies have a permissive license (C-PERMISSIVE)](https://rust-lang.github.io/api-guidelines/necessities.html#c-permissive). <!-- API:117 -->
- If choosing Rust's dual license, declare it in Cargo metadata, include both license texts, and describe the choice in the README. — [Rust API Guidelines: Crate and its dependencies have a permissive license (C-PERMISSIVE)](https://rust-lang.github.io/api-guidelines/necessities.html#c-permissive). <!-- API:118 -->
- Do not equate Apache-only licensing with the interoperability of Rust's dual-license choice. — [Rust API Guidelines: Crate and its dependencies have a permissive license (C-PERMISSIVE)](https://rust-lang.github.io/api-guidelines/necessities.html#c-permissive). <!-- API:119 -->
- For a permissively licensed crate, normally choose dependencies with permissive licenses too. — [Rust API Guidelines: Crate and its dependencies have a permissive license (C-PERMISSIVE)](https://rust-lang.github.io/api-guidelines/necessities.html#c-permissive). <!-- API:120 -->

## Types and data

- Provide applicable `Copy`, `Clone`, `Eq`, `PartialEq`, `Ord`, `PartialOrd`, `Hash`, `Debug`, `Display`, and `Default` implementations. — [Rust API Guidelines: Types eagerly implement common traits (C-COMMON-TRAITS)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-common-traits). <!-- API:022 -->
- Offer a zero-argument `new` when meaningful even if it duplicates `Default`. — [Rust API Guidelines: Types eagerly implement common traits (C-COMMON-TRAITS)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-common-traits). <!-- API:023 -->
- Express suitable conversions with `From`, `TryFrom`, `AsRef`, and `AsMut` implementations. — [Rust API Guidelines: Conversions use the standard traits From, AsRef, AsMut (C-CONV-TRAITS)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-conv-traits). <!-- API:024 -->
- Implement the `From` or `TryFrom` side so blanket implementations supply `Into` or `TryInto`. — [Rust API Guidelines: Conversions use the standard traits From, AsRef, AsMut (C-CONV-TRAITS)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-conv-traits). <!-- API:025 -->
- Let custom collections be constructed from iterators through `FromIterator`. — [Rust API Guidelines: Collections implement FromIterator and Extend (C-COLLECT)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-collect). <!-- API:026 -->
- Let custom collections absorb iterator elements through `Extend`. — [Rust API Guidelines: Collections implement FromIterator and Extend (C-COLLECT)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-collect). <!-- API:027 -->
- Support appropriate Serde serialization and deserialization for data structures. — [Rust API Guidelines: Data structures implement Serde's Serialize, Deserialize (C-SERDE)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-serde). <!-- API:028 -->
- Maintain `Send` and `Sync` wherever their safety requirements hold. — [Rust API Guidelines: Types are Send and Sync where possible (C-SEND-SYNC)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-send-sync). <!-- API:030 -->
- Support binary, octal, and both hexadecimal formatting traits for numeric or bitflag types with meaningful bit operations. — [Rust API Guidelines: Binary number types provide Hex, Octal, Binary formatting (C-NUM-FMT)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-num-fmt). <!-- API:038 -->
- Accept generic `Read` or `Write` values by value so an owner or mutable borrow can be supplied. — [Rust API Guidelines: Generic reader/writer functions take R: Read and W: Write by value (C-RW-VALUE)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-rw-value). <!-- API:039 -->
- Expose smart-pointer-specific operations as associated functions so they do not shadow pointee methods. — [Rust API Guidelines: Smart pointers do not add inherent methods (C-SMART-PTR)](https://rust-lang.github.io/api-guidelines/predictability.html#c-smart-ptr). <!-- API:067 -->
- Attach a conversion to the more specialized type whose invariants motivate it. — [Rust API Guidelines: Conversions live on the most specific type involved (C-CONV-SPECIFIC)](https://rust-lang.github.io/api-guidelines/predictability.html#c-conv-specific). <!-- API:069 -->
- Use a receiver method for behavior naturally belonging to one value. — [Rust API Guidelines: Functions with a clear receiver are methods (C-METHOD)](https://rust-lang.github.io/api-guidelines/predictability.html#c-method). <!-- API:070 -->
- Return multiple results in a tuple or struct instead of writing through out-parameters. — [Rust API Guidelines: Functions do not take out-parameters (C-NO-OUT)](https://rust-lang.github.io/api-guidelines/predictability.html#c-no-out). <!-- API:071 -->
- Keep mutable output buffers when reusing or modifying caller storage is the operation's purpose. — [Rust API Guidelines: Functions do not take out-parameters (C-NO-OUT)](https://rust-lang.github.io/api-guidelines/predictability.html#c-no-out). <!-- API:072 -->
- Overload an operator only when its customary meaning and algebraic laws fit the operation. — [Rust API Guidelines: Operator overloads are unsurprising (C-OVERLOAD)](https://rust-lang.github.io/api-guidelines/predictability.html#c-overload). <!-- API:073 -->
- Implement `Deref` and `DerefMut` only for smart-pointer semantics. — [Rust API Guidelines: Only smart pointers implement Deref and DerefMut (C-DEREF)](https://rust-lang.github.io/api-guidelines/predictability.html#c-deref). <!-- API:074 -->
- Define constructors as inherent associated functions without a receiver. — [Rust API Guidelines: Constructors are static, inherent methods (C-CTOR)](https://rust-lang.github.io/api-guidelines/predictability.html#c-ctor). <!-- API:075 -->
- Make parameterless `new` and `Default` equivalent when both are provided. — [Rust API Guidelines: Constructors are static, inherent methods (C-CTOR)](https://rust-lang.github.io/api-guidelines/predictability.html#c-ctor). <!-- API:079 -->
- Accept ownership when needed instead of borrowing a value only to clone it. — [Rust API Guidelines: Caller decides where to copy and place data (C-CALLER-CONTROL)](https://rust-lang.github.io/api-guidelines/flexibility.html#c-caller-control). <!-- API:081 -->
- Borrow inputs when retaining ownership would serve no purpose. — [Rust API Guidelines: Caller decides where to copy and place data (C-CALLER-CONTROL)](https://rust-lang.github.io/api-guidelines/flexibility.html#c-caller-control). <!-- API:082 -->
- Require `Copy` for semantic necessity, not as a proxy for cheap cloning. — [Rust API Guidelines: Caller decides where to copy and place data (C-CALLER-CONTROL)](https://rust-lang.github.io/api-guidelines/flexibility.html#c-caller-control). <!-- API:083 -->
- Use the least demanding useful generic bounds rather than fixing an unnecessary container representation. — [Rust API Guidelines: Functions minimize assumptions about parameters by using generics (C-GENERIC)](https://rust-lang.github.io/api-guidelines/flexibility.html#c-generic). <!-- API:084 -->
- Weigh generic flexibility, dispatch, layout, and inference against larger binaries and more complicated signatures. — [Rust API Guidelines: Functions minimize assumptions about parameters by using generics (C-GENERIC)](https://rust-lang.github.io/api-guidelines/flexibility.html#c-generic). <!-- API:085 -->
- Decide during trait design whether callers should be able to use trait objects. — [Rust API Guidelines: Traits are object-safe if they may be useful as a trait object (C-OBJECT)](https://rust-lang.github.io/api-guidelines/flexibility.html#c-object). <!-- API:086 -->
- Keep object-facing methods dyn-compatible, replacing obstructive method generics with object inputs or outputs where appropriate. — [Rust API Guidelines: Traits are object-safe if they may be useful as a trait object (C-OBJECT)](https://rust-lang.github.io/api-guidelines/flexibility.html#c-object). <!-- API:087 -->
- Exclude individual helpers from trait-object use with `Self: Sized` when needed. — [Rust API Guidelines: Traits are object-safe if they may be useful as a trait object (C-OBJECT)](https://rust-lang.github.io/api-guidelines/flexibility.html#c-object). <!-- API:088 -->
- Use newtypes to separate distinct meanings carried by the same primitive representation. — [Rust API Guidelines: Newtypes provide static distinctions (C-NEWTYPE)](https://rust-lang.github.io/api-guidelines/type-safety.html#c-newtype). <!-- API:089 -->
- Choose argument types that express choices and invariants instead of relying on ambiguous primitives or optional values. — [Rust API Guidelines: Arguments convey meaning through types, not bool or Option (C-CUSTOM-TYPE)](https://rust-lang.github.io/api-guidelines/type-safety.html#c-custom-type). <!-- API:090 -->
- Represent independently combinable flags with bitflags rather than a single-choice enum. — [Rust API Guidelines: Types for a set of flags are bitflags, not enums (C-BITFLAG)](https://rust-lang.github.io/api-guidelines/type-safety.html#c-bitflag). <!-- API:091 -->
- Use a separate builder for many arguments, optional settings, compound inputs, or alternative construction paths. — [Rust API Guidelines: Builders enable construction of complex values (C-BUILDER)](https://rust-lang.github.io/api-guidelines/type-safety.html#c-builder). <!-- API:092 -->
- Require essential inputs when creating a builder and support fluent configuration of the rest. — [Rust API Guidelines: Builders enable construction of complex values (C-BUILDER)](https://rust-lang.github.io/api-guidelines/type-safety.html#c-builder). <!-- API:093 -->
- Make construction and side effects explicit terminal builder operations. — [Rust API Guidelines: Builders enable construction of complex values (C-BUILDER)](https://rust-lang.github.io/api-guidelines/type-safety.html#c-builder). <!-- API:094 -->
- Prefer reusable builders whose setters borrow mutably when construction need not consume the builder. — [Rust API Guidelines: Builders enable construction of complex values (C-BUILDER)](https://rust-lang.github.io/api-guidelines/type-safety.html#c-builder). <!-- API:095 -->
- For consuming builders, have fluent setters consume and return `self` so chaining remains possible. — [Rust API Guidelines: Builders enable construction of complex values (C-BUILDER)](https://rust-lang.github.io/api-guidelines/type-safety.html#c-builder). <!-- API:096 -->
- Reject invalid inputs where practical rather than tolerating malformed values. — [Rust API Guidelines: Functions validate their arguments (C-VALIDATE)](https://rust-lang.github.io/api-guidelines/dependability.html#c-validate). <!-- API:097 -->
- Encode validity in types first, using runtime checks for invariants the types cannot express. — [Rust API Guidelines: Functions validate their arguments (C-VALIDATE)](https://rust-lang.github.io/api-guidelines/dependability.html#c-validate). <!-- API:098 -->
- Use debug assertions for costly checks intended to disappear from production builds. — [Rust API Guidelines: Functions validate their arguments (C-VALIDATE)](https://rust-lang.github.io/api-guidelines/dependability.html#c-validate). <!-- API:099 -->
- Implement `Debug` for nearly all public types. — [Rust API Guidelines: All public types implement Debug (C-DEBUG)](https://rust-lang.github.io/api-guidelines/debuggability.html#c-debug). <!-- API:105 -->
- Ensure `Debug` emits useful nonempty output even for values with no conceptual contents. — [Rust API Guidelines: Debug representation is never empty (C-DEBUG-NONEMPTY)](https://rust-lang.github.io/api-guidelines/debuggability.html#c-debug-nonempty). <!-- API:106 -->
- Seal traits that must not admit downstream implementations. — [Rust API Guidelines: Sealed traits protect against downstream implementations (C-SEALED)](https://rust-lang.github.io/api-guidelines/future-proofing.html#c-sealed). <!-- API:107 -->
- Keep fields private unless passive public data is the intended API, preserving validation and representation flexibility. — [Rust API Guidelines: Structs have private fields (C-STRUCT-PRIVATE)](https://rust-lang.github.io/api-guidelines/future-proofing.html#c-struct-private). <!-- API:110 -->
- Wrap complex implementation types in newtypes when the public contract should promise less. — [Rust API Guidelines: Newtypes encapsulate implementation details (C-NEWTYPE-HIDE)](https://rust-lang.github.io/api-guidelines/future-proofing.html#c-newtype-hide). <!-- API:111 -->
- Consider an opaque `impl Trait` result when it captures the intended guarantees. — [Rust API Guidelines: Newtypes encapsulate implementation details (C-NEWTYPE-HIDE)](https://rust-lang.github.io/api-guidelines/future-proofing.html#c-newtype-hide). <!-- API:112 -->
- Avoid redundant or derivable bounds on generic data-type definitions. — [Rust API Guidelines: Data structures do not duplicate derived trait bounds (C-STRUCT-BOUNDS)](https://rust-lang.github.io/api-guidelines/future-proofing.html#c-struct-bounds). <!-- API:113 -->
- Do not add `Clone`, comparison, formatting, `Default`, `Error`, or Serde bounds to data types solely because some implementations need them. — [Rust API Guidelines: Data structures do not duplicate derived trait bounds (C-STRUCT-BOUNDS)](https://rust-lang.github.io/api-guidelines/future-proofing.html#c-struct-bounds). <!-- API:114 -->
- Retain definition-level bounds needed by associated types, unsized values, or `Drop`. — [Rust API Guidelines: Data structures do not duplicate derived trait bounds (C-STRUCT-BOUNDS)](https://rust-lang.github.io/api-guidelines/future-proofing.html#c-struct-bounds). <!-- API:115 -->

## Errors

- Make public error types implement `Error` together with `Send` and `Sync`. — [Rust API Guidelines: Error types are meaningful and well-behaved (C-GOOD-ERR)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-good-err). <!-- API:032 -->
- Use `Send + Sync + 'static` error trait objects when cross-thread handling or downcasting is needed. — [Rust API Guidelines: Error types are meaningful and well-behaved (C-GOOD-ERR)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-good-err). <!-- API:033 -->
- Return a dedicated, meaningful error type instead of `()`, using a unit struct when no payload is needed. — [Rust API Guidelines: Error types are meaningful and well-behaved (C-GOOD-ERR)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-good-err). <!-- API:034 -->
- Give errors informative `Display` formatting. — [Rust API Guidelines: Error types are meaningful and well-behaved (C-GOOD-ERR)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-good-err). <!-- API:035 -->
- Keep error-message text brief, lowercase, and free of terminal punctuation. — [Rust API Guidelines: Error types are meaningful and well-behaved (C-GOOD-ERR)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-good-err). <!-- API:036 -->
- Supply error text through `Display`, avoiding the deprecated `Error::description` method. — [Rust API Guidelines: Error types are meaningful and well-behaved (C-GOOD-ERR)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-good-err). <!-- API:037 -->
- Keep destructor execution infallible. — [Rust API Guidelines: Destructors never fail (C-DTOR-FAIL)](https://rust-lang.github.io/api-guidelines/dependability.html#c-dtor-fail). <!-- API:102 -->
- Provide explicit fallible closing when cleanup errors matter; if it was omitted, `Drop` may log or ignore those errors. — [Rust API Guidelines: Destructors never fail (C-DTOR-FAIL)](https://rust-lang.github.io/api-guidelines/dependability.html#c-dtor-fail). <!-- API:103 -->

## Testing

- Review raw-pointer types for thread safety and test that promised auto-traits remain available. — [Rust API Guidelines: Types are Send and Sync where possible (C-SEND-SYNC)](https://rust-lang.github.io/api-guidelines/interoperability.html#c-send-sync). <!-- API:031 -->
- Exercise item-generating macros at both module and function scope. — [Rust API Guidelines: Item macros work anywhere that items are allowed (C-ANYWHERE)](https://rust-lang.github.io/api-guidelines/macros.html#c-anywhere). <!-- API:045 -->

## Performance

- Expose useful intermediate results when that prevents clients from recomputing them. — [Rust API Guidelines: Functions expose intermediate results to avoid duplicate work (C-INTERMEDIATE)](https://rust-lang.github.io/api-guidelines/flexibility.html#c-intermediate). <!-- API:080 -->
- Keep destructors nonblocking, moving potentially blocking preparation or shutdown into a separate operation. — [Rust API Guidelines: Destructors that may block have alternatives (C-DTOR-BLOCK)](https://rust-lang.github.io/api-guidelines/dependability.html#c-dtor-block). <!-- API:104 -->

## Security

- Consider an unsafe `unchecked` accessor when callers can legitimately bypass its checks. — [Rust API Guidelines: Getter names follow Rust convention (C-GETTER)](https://rust-lang.github.io/api-guidelines/naming.html#c-getter). <!-- API:014 -->
- List every obligation imposed on unsafe callers in a `Safety` section. — [Rust API Guidelines: Function docs include error, panic, and safety considerations (C-FAILURE)](https://rust-lang.github.io/api-guidelines/documentation.html#c-failure). <!-- API:057 -->
- Skip validation only when correctness is independently established and the speed benefit warrants it. — [Rust API Guidelines: Functions validate their arguments (C-VALIDATE)](https://rust-lang.github.io/api-guidelines/dependability.html#c-validate). <!-- API:101 -->

## Language-specific pitfalls

- Design macro inputs to resemble familiar Rust and the syntax they generate. — [Rust API Guidelines: Input syntax is evocative of the output (C-EVOCATIVE)](https://rust-lang.github.io/api-guidelines/macros.html#c-evocative). <!-- API:041 -->
- Allow attributes, including conditional compilation, on individual macro-generated items. — [Rust API Guidelines: Item macros compose well with attributes (C-MACRO-ATTR)](https://rust-lang.github.io/api-guidelines/macros.html#c-macro-attr). <!-- API:042 -->
- Permit deriving traits on structs and enums emitted by macros. — [Rust API Guidelines: Item macros compose well with attributes (C-MACRO-ATTR)](https://rust-lang.github.io/api-guidelines/macros.html#c-macro-attr). <!-- API:043 -->
- Make item-producing macros valid wherever ordinary items may appear. — [Rust API Guidelines: Item macros work anywhere that items are allowed (C-ANYWHERE)](https://rust-lang.github.io/api-guidelines/macros.html#c-anywhere). <!-- API:044 -->
- Accept normal Rust visibility in macros and default generated items to private visibility. — [Rust API Guidelines: Item macros support visibility specifiers (C-MACRO-VIS)](https://rust-lang.github.io/api-guidelines/macros.html#c-macro-vis). <!-- API:046 -->
- Parse type fragments correctly for primitives, relative and absolute paths, parent paths, and generic types. — [Rust API Guidelines: Type fragments are flexible (C-MACRO-TY)](https://rust-lang.github.io/api-guidelines/macros.html#c-macro-ty). <!-- API:047 -->
- Treat removal or signature changes of public sealed-trait methods as compatibility breaks. — [Rust API Guidelines: Sealed traits protect against downstream implementations (C-SEALED)](https://rust-lang.github.io/api-guidelines/future-proofing.html#c-sealed). <!-- API:109 -->
- Do not call a version-1.0-or-later API stable while it exposes unstable dependency types. — [Rust API Guidelines: Public dependencies of a stable crate are stable (C-STABLE)](https://rust-lang.github.io/api-guidelines/necessities.html#c-stable). <!-- API:116 -->
